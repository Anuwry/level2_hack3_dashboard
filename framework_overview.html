Pose Similarity Algorithms

1 normalizePose(kp)
Translates all joints so Hips = [0,0,0]. Scale = first available distance from: (Hips→Neck) → (LeftArm→RightArm) → (LeftUpLeg→RightUpLeg). Returns null if < 8 joints valid.
2 poseSimilarity(a, b, weights)
Both poses must already be normalized. Formula: 1 / (1 + weightedAvgDist)
  • Iterates JOINT_NAMES_17, skips joints with weight ≤ 0
  • Weighted average: Σ(dist × w) / Σ(w)
  • Returns 0 if total weight < 2
  • Range: 0–1, where 1.0 = perfect match
3 matchLabelsToFrames — Best-Any-Frame
Speed-invariant matching. For each session frame, score against ALL label poses, keep the best. Group consecutive hits (gap tolerance = max(3, floor(cooldown/3))). Each group → one event centered on peak score frame.
// Old: sequential window → score 0.64 cross-session
// New: best-any-frame → score 0.84+ cross-session
hitFrames ← frames where max(sim(frame, labelSeq[*])) ≥ 0.78
4 computeStrokeAlignment — DTW
Dynamic Time Warping for monotonic label→session frame mapping.
  • Cost matrix M×N: cost[i][j] = 1 - similarity(labelFrame[i], sessionFrame[j])
  • Fill: dtw[i][j] = cost + min(diag, up, left)
  • Traceback (M-1, N-1) → (0,0) → path → labelToSession[] array
  • Attaches sessionToLabel Map for O(1) reverse lookup during playback
  • Self-match gives label[k]→session[k] with ~100% scores
for i in M: for j in N:
  dtw[i][j] = (1-sim(i,j)) + min(diag, up, left)
result.sessionToLabel = Map<sessionIdx, labelIdx>
5 Compare Mode — Sync Strategy
Two modes depending on context:
  • Event-window (click/auto-event): linear interpolation within event range: t = (frame - start) / (end - start). Then event-scoped DTW on only those frames for accurate per-pose sync.
  • Manual preview: full-session DTW sessionToLabel map — O(1) lookup + nearest-frame fallback.

Design Decisions

JS normalization over backend rounded data
computeStrokeAlignment uses label.frames[i].keypoints_17 + frontend normalizePose() instead of backend's pre-normalized normalized_sequence.pose (rounded to 5dp in Python). This gives bit-exact self-match scores (~100%) because both poses go through the same JS float operations.
DTW for analysis, event-progress for playback
Full-session DTW (all frames × 46 label frames) is expensive but correct for score wave display. For real-time playback within an event window, a second lighter DTW scoped to the event's frames gives smooth sync without artifacts from DTW mapping frames outside the event range to wrong label frames.
Always-mounted AvatarViewer
The normal 3D view (AvatarViewer) is always in the DOM — hidden with invisible pointer-events-none CSS when compare mode is on. If unmounted via conditional rendering, Three.js scene is destroyed and must be re-initialized on toggle, causing a visible flash.
No auto-trigger during playback
An earlier implementation auto-activated compare mode when the playhead hit a yellow marker during playback. Removed by user request — compare only activates on explicit click of a timeline marker or ▶ Compare button.

🤯 Fun Facts — How MediaPipe Sees Your Body

MediaPipe BlazePose reconstructs a full 3D skeleton from a single 2D camera frame in ~5 ms on CPU. Here's the magic behind every number it produces.

👈👉

Left vs Right — It's Anatomy, Not the Camera

MediaPipe never calls a joint "left" based on where it appears on screen. Instead, BlazePose was trained on thousands of annotated 3D human skeletons where anatomical left/right is ground truth regardless of the person's facing direction.

During inference the model sees both shoulders, both hips, and the full body topology at once. It infers side assignment from the global body geometry: if the left shoulder is to the camera's right because the person is facing away, BlazePose still labels it LEFT_SHOULDER.

⚡ Consequence for us: our joint names (LeftArm, RightHand, …) stay correct even when the player turns around or is filmed from behind. No mirroring needed.
📐

Z-Depth — Guessing 3D from a Flat Photo

The camera captures no depth information — it's a pure 2D projection. MediaPipe hallucinates the Z axis using learned body-proportion priors: average shoulder width ≈ 40 cm, forearm length relative to upper arm, hip width, etc.

It combines three cues:

  • Perspective foreshortening — a raised elbow appears shorter in 2D; the model learned how much shorter per degree of rotation
  • Occlusion / overlap — if the forearm crosses the torso, that side is probably in front
  • Global pose prior — the neural net learned thousands of realistic poses; it picks the most plausible 3D lift
⚡ Result: X and Y are accurate to a few mm. Z is accurate to a few cm for slow, clear movements — but can jump 10–15 cm frame-to-frame during fast strokes. That's why we run a Kalman filter on top.
🎯

Why the Kalman Filter?

MediaPipe outputs a new skeleton independently every frame — no temporal memory. A joint that is briefly occluded or at a pose the model finds ambiguous can teleport several centimetres in one frame.

The Kalman filter maintains a 6-state model (position + velocity) per joint. It predicts where the joint should be next frame based on velocity, then blends that prediction with the raw MediaPipe reading, weighted by how trustworthy each source is. Fast, smooth trajectories — especially for Z.

🏋️

The Origin Lives at Your Hips

MediaPipe's world-space origin is wherever the person happens to stand in the room. Two recordings made at different distances from the camera produce wildly different absolute coordinates.

We solve this in normalizePose(): subtract the Hips midpoint so every pose is centered at [0,0,0], then divide by body scale (Hips→Neck distance). After this step a 1.60 m player and a 1.95 m player produce comparable numbers — and Hips is always exactly [0, 0, 0] (hence its weight = 0; scoring it would always give 100%).

⚡

5 ms to a Full 3D Human

BlazePose uses a two-stage architecture:

  1. Pose detector — finds the bounding box of the person in the frame (runs only once or when the person is lost)
  2. Landmark model — given the crop, predicts 33 landmarks × (x, y, z, visibility) in one forward pass

We map 33 MediaPipe landmarks → 17 biomechanical joints (e.g. average of left/right hip → Hips). The whole pipeline — decode JPEG → MediaPipe → Kalman → 17-joint dict — runs in one FastAPI request handler.

MediaPipe World Coordinates → Three.js

MediaPipe outputs world coordinates (not image-pixel coordinates). The axes are:

Axis Direction Three.js
X Camera right → X (unchanged)
Y Down ↓ −Y (flipped up)
Z Into camera (toward lens) −Z (flipped forward)

In code (extractor.py → frontend):

# backend: raw MediaPipe → stored as-is
kp["RightHand"] = [x, y, z]

// frontend: Three.js scene
const pos = [x, -y, -z]

Z increases as the joint moves toward the camera lens. A raised hand in front of the body has a larger (more positive) Z than the hip. After our flip, it becomes −Z which is "forward" in Three.js right-hand coordinates.
